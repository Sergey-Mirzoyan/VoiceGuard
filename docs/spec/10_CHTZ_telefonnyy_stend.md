# ЧТЗ-10. Телефонный стенд (Asterisk + ARI)

Основание: общее ТЗ, разделы 4, 10.5, 12; концепт, раздел 4. Зависимости: ЧТЗ-09.

## 1. Цель

Стенд, имитирующий сеть оператора: звонок идёт через АТС, копия голоса звонящего уходит в движок, при вердикте «подозрение» абонент (и только он) слышит предупреждение. Это основа демонстрации на питче.

## 2. Объём работ

Входит: контейнер Asterisk 20 с PJSIP и ARI, диалплан, ARI-приложение на Python, звонящий-бот, проигрывание предупреждения, имитация SMS, инструкция по подключению софтфона, сквозной автотест.

Не входит: реальная интеграция с оператором, поддержка AMR внутри Asterisk (кодек AMR имитируется в движке, FR-06).

## 3. Функциональные требования

**FR-01. Asterisk.** `docker/asterisk/`: Dockerfile (Asterisk 20 LTS), конфигурация `pjsip.conf`, `extensions.conf`, `ari.conf`, `http.conf`, `rtp.conf`. Абоненты PJSIP:

| Номер | Роль |
|---|---|
| 100 | Абонент (софтфон на ноутбуке или смартфоне; например Linphone или Zoiper) |
| 101 | Живой звонящий (второй софтфон — для демонстрации живой речи) |
| 900 | Автоответчик для автотестов: отвечает и ждёт, ничего не записывает |

Кодек между Asterisk и софтфонами — G.711 (µ-law или A-law). Диапазон RTP-портов и адрес для NAT задаются переменными окружения.

**FR-02. Маршрут звонка.** Любой звонок на 100 или 900 попадает в Stasis-приложение `voiceguard`. Приложение (`voiceguard.telephony.ari_app`):

1. получает `StasisStart` канала звонящего, создаёт вызов к абоненту, основной смешивающий мост и добавляет оба канала после ответа;
2. создаёт в движке сессию с `rtp=true` и `channel_sim` из конфигурации (по умолчанию `amrnb_12.2`);
3. создаёт snoop-канал на канале звонящего, получающий только его голос (`spy=in`), и externalMedia-канал на выделенный движком RTP-порт в формате `slin16`; соединяет их отдельным мостом. Голос абонента в движок не попадает;
4. подписывается на события сессии (WebSocket движка или колбэк `on_verdict` через HTTP-вебхук `POST /telephony/verdict` — выбор за агентом, с обоснованием);
5. при вердикте `suspicious` создаёт snoop-канал на канале абонента с направлением `whisper` к абоненту и проигрывает `sound:vg-warning-{lang}`; звонящий предупреждение не слышит. Направление `whisper` подбирается и проверяется вручную, результат фиксируется в README стенда;
6. имитирует SMS: пишет в журнал и публикует событие `sms` в движке (панель его покажет) с текстом из конфигурации;
7. при завершении звонка удаляет сессию, мосты и вспомогательные каналы.

**FR-03. Предупреждение.** `docker/asterisk/sounds/`: `vg-warning-hy.wav`, `vg-warning-ru.wav`, `vg-warning-en.wav` (slin16, 16 кГц): два тона 440 Гц по 300 мс с паузой 200 мс, затем фраза. Тексты:

- hy: «Ուշադրություն։ Զանգահարողի ձայնը կարող է արհեստականորեն ստեղծված լինել։» (текст проверяет носитель языка со стороны заказчика);
- ru: «Внимание: голос звонящего может быть искусственно создан»;
- en: «Warning: the caller's voice may be artificially generated».

Агент генерирует временные файлы (тоны + синтез фразы любым доступным TTS) и оставляет инструкцию, как заменить их записью диктора. Язык выбирается параметром `telephony.warning_lang` (по умолчанию `hy`).

**FR-04. Звонящий-бот.** `python -m voiceguard.telephony call --file path.wav --to 100 [--label live|spoof]`: конвертирует файл в формат Asterisk (slin16), кладёт в каталог звуков контейнера, через ARI инициирует звонок, в котором «звонящий» проигрывает файл и кладёт трубку. Звонок бота проходит тот же маршрут FR-02, что и звонок с софтфона 101. `--batch список.csv` выполняет серию звонков с паузой.

**FR-05. Метаданные звонка.** В сессии движка сохраняются: время начала, номер вызываемого, метка `label` (для бота), итоговый вердикт и время до вердикта. Эти данные показывает панель; в журнале и событиях нет звука.

**FR-06. Имитация канала.** Поскольку AMR внутри Asterisk нестандартен, телефонный кодек мобильной сети имитируется в движке (`channel_sim`), а на стенде голос идёт в G.711. Это ограничение описывается в README и в демо-сценарии.

**FR-07. Тестовый режим движка.** Параметр `engine.test_mode=true` подменяет детекторы заглушкой: звонки с меткой `spoof` дают `llr=+2`, с меткой `live` — `llr=−2` на каждом сегменте. Режим нужен, чтобы проверять телефонную часть независимо от точности детекторов.

## 4. Критерии приёмки

- **AC-01.** `docker compose up asterisk engine` поднимает стенд; софтфон регистрируется как 100 по инструкции из README (проверка вручную, результат — скриншот или журнал в отчёте).
- **AC-02.** Автотест в тестовом режиме (FR-07): бот звонит на 900 с файлом `spoof`; в течение 10 с приходит событие ARI `PlaybackStarted` для `vg-warning` на snoop-канале абонента. Для файла `live` предупреждение не проигрывается, вердикт `normal`.
- **AC-03.** Автотест: в движок попадает только голос звонящего. Бот проигрывает тон 1 кГц, автоответчик 900 — тон 2 кГц (тестовый контекст диалплана); спектр потока, полученного движком, содержит 1 кГц и не содержит 2 кГц (разница не менее 30 дБ).
- **AC-04.** Ручная проверка: при звонке с 101 на 100 и вердикте `suspicious` (тестовый режим) абонент 100 слышит предупреждение, звонящий 101 — нет.
- **AC-05.** После 20 последовательных звонков бота в движке нет «висящих» сессий, в Asterisk нет оставшихся мостов и snoop-каналов.
