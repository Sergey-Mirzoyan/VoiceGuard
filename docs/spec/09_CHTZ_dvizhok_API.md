# ЧТЗ-09. Потоковый движок и API

Основание: общее ТЗ, разделы 4, 7, 8, 10.5, 12. Зависимости: ЧТЗ-08.

## 1. Цель

Сервис, который принимает аудиопоток звонящего в реальном времени, каждую секунду речи обновляет оценку и выдаёт вердикт. Сервис используется телефонным стендом (ЧТЗ-10) и панелью (ЧТЗ-11). Звук на диск не записывается.

## 2. Объём работ

Входит: класс сессии анализа, планировщик вычислений D1/D2, приём RTP (для стенда), REST и WebSocket API, хранение событий сессий в памяти, метрики производительности, Dockerfile.

Не входит: управление звонками Asterisk (ЧТЗ-10), интерфейс (ЧТЗ-11).

## 3. Функциональные требования

**FR-01. Сессия.** `voiceguard.engine.Session(session_id, sr, channel_sim: ChannelSpec | None, cfg)`:

- `push(pcm: np.ndarray)` принимает кадры PCM16/float по 20 мс;
- если задан `channel_sim`, поток проходит `StreamTranscoder` (ЧТЗ-03) — имитация AMR на стенде;
- VAD и накопление речи; по заполнении сегмента 1 с запускается анализ;
- результат каждого сегмента — `WindowScore` (раздел 7 общего ТЗ), он добавляется в список событий сессии;
- после вердикта `suspicious` вызывается колбэк `on_verdict(session_id, WindowScore)` (для стенда);
- звук хранится только в кольцевом буфере в памяти, размер не более `max(segment_B_s, 5)` секунд.

**FR-02. Планировщик D2.** Обучение 12 предсказателей на каждый сегмент может не укладываться в реальное время. Режимы (`engine.stream_d2_checks`):

- `all` — все проверки варианта из конфигурации;
- `reduced` — подмножество проверок из `engine.d2_reduced` (например, `A_bit_w16_fwd`, `A_block_w16_fwd`, `A_bit_w32_bwd`), m пересчитывается;
- `async` — D2 считается в пуле процессов; сегмент без готового D2 обновляет SPRT только по D1, а результат D2 учитывается при поступлении (событие помечается `late_d2=true`).

Режим по умолчанию выбирается по замерам ЧТЗ-05 так, чтобы выполнялось NFR-01, и обосновывается в отчёте о сдаче.

**FR-03. REST API** (FastAPI, префикс `/v1`):

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | Состояние, версии моделей |
| GET | `/passport` | Паспорт детектора (ЧТЗ-08) |
| POST | `/analyze` | Файл (wav/flac/ogg/m4a) + параметр `channel` → полный анализ: список `WindowScore`, итоговый вердикт, D2-детали по сегментам |
| POST | `/sessions` | Создать сессию: `sr`, `channel_sim`, `rtp`, `meta` (словарь метаданных звонка: номер, метка бота) → `session_id`, `rtp_port` |
| GET | `/sessions/{id}/events?since=k` | События сессии начиная с номера k |
| POST | `/sessions/{id}/events` | Внешнее событие от стенда (тип `sms`, `call_ended`) с текстом; сохраняется в ленте событий |
| DELETE | `/sessions/{id}` | Закрыть сессию, очистить буфер |
| GET | `/sessions` | Активные и недавние сессии (последние 50, только метаданные и события) |

**FR-04. WebSocket.** `/v1/stream/{session_id}`: клиент шлёт бинарные кадры PCM16 little-endian; сервер шлёт JSON `WindowScore` по мере готовности. Закрытие соединения закрывает сессию.

**FR-05. Приёмник RTP.** `voiceguard.engine.rtp.RtpReceiver(port_range)`: выделяет UDP-порт под сессию, принимает RTP с полезной нагрузкой `slin16` (16 кГц, big-endian, как отдаёт Asterisk externalMedia) или `ulaw`, упорядочивает пакеты по sequence number с буфером 60 мс, передаёт PCM в `Session.push`. `POST /v1/sessions` с параметром `rtp=true` возвращает выделенный `rtp_port`.

**FR-06. Хранение событий.** Каждое событие — JSON с полями `seq`, `type` (`window`, `verdict`, `sms`, `call_ended`) и данными (для `window` — поля `WindowScore`). События хранятся в памяти не более 1 часа после закрытия сессии (для панели), затем удаляются. Содержимое — только числа и вердикты, без звука и текста.

**FR-07. Метрики.** `GET /v1/metrics` (формат Prometheus): число активных сессий, время обработки сегмента D1, D2, SPRT (гистограммы), RTF, число отброшенных пакетов RTP.

**FR-08. Dockerfile.** `docker/Dockerfile.engine` на основе базового образа ЧТЗ-01; запуск `uvicorn voiceguard.engine.api:app`; модели и эталоны монтируются томом.

## 4. Нефункциональные требования

- **NFR-01.** Сквозная обработка в выбранном режиме FR-02: RTF ≤ 0,5 на 4 ядрах CPU при 4 одновременных сессиях.
- **NFR-02.** Задержка от конца сегмента 1 с речи до события `WindowScore` (D1 + SPRT) — не более 300 мс (p95).
- **NFR-03.** При `debug.save_audio = false` сервис не создаёт файлов со звуком (проверяется тестом по списку открытых на запись файлов либо по каталогу временных файлов).

## 5. Критерии приёмки

- **AC-01.** Тест: `POST /analyze` на клипе из фикстуры возвращает события и итоговый вердикт; повторный вызов даёт идентичный результат.
- **AC-02.** Тест: WebSocket-клиент, подающий клип в реальном времени (кадры 20 мс с паузой 20 мс), получает события каждую секунду речи; результаты совпадают с `/analyze` по вердикту.
- **AC-03.** Тест: RTP-клиент (генератор пакетов в тесте) с перестановкой 5% пакетов даёт тот же вердикт, что и упорядоченный поток.
- **AC-04.** Нагрузочный тест: 4 параллельные сессии по 30 с — RTF и задержки в пределах NFR-01, NFR-02; результаты в отчёте о сдаче.
- **AC-05.** Тест NFR-03.
